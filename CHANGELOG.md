# Changelog

All notable changes to 3329lens (the `lens3329` crate) are recorded here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project uses [Semantic Versioning](https://semver.org/). Before 1.0, a
breaking change bumps the minor version (0.1 → 0.2).

## [0.2.2] - Unreleased

### Security

- **Only one version of each package in a lockfile was checked against
  advisories.** When a `Cargo.lock`, npm lockfile, `poetry.lock` or
  `Pipfile.lock` contained several versions of the same package, which is
  common for Cargo and npm projects, 3329lens kept the first version it read
  and ignored the rest. Advisories affecting the other versions were not
  reported, and `--fail-on` could exit 0 when it should have exited 2.
  Every locked version now gets its own finding and is checked on its own.
  Scans of projects like this will report more findings, and possibly more
  vulnerabilities, than 0.2.1 did. Upgrading is recommended for everyone who
  uses `--advisory-db`.

### Fixed

- For npm projects, a declared dependency's version now comes from the copy
  installed at the top level (`node_modules/<name>`), which is the one the
  project imports. Previously it could come from a nested copy that happened
  to be listed first.
- The migration plan exported from the dashboard's Migration view (`e`) now
  ends with "Generated by 3329lens" and the version. It said "Generated by
  Slow Lynx Cryptography Discovery", a leftover from the project 3329lens was
  extracted from, like the report names fixed in 0.2.1.

### Added

- `lockfile::LockedPackages`, every resolved version of every package in a
  lockfile, and the functions that return it: `parse_cargo_lock_all`,
  `parse_npm_lock_all`, `parse_poetry_lock_all`, `parse_pipfile_lock_all`,
  `resolve_from_sibling_lock_all`, `resolve_npm_from_sibling_lock_all` and
  `resolve_pypi_from_sibling_lock_all`.

### Deprecated

- The single-version lockfile functions (`parse_cargo_lock`,
  `resolve_from_sibling_lock`, `parse_npm_lock`, `resolve_npm_from_sibling_lock`,
  `parse_poetry_lock`, `parse_pipfile_lock`, `resolve_pypi_from_sibling_lock`).
  They behave exactly as in 0.2.1, but because they keep only one version of
  each package, code that uses them for advisory checks has the same gap
  described above. Use the `_all` functions instead.

## [0.2.1] - 2026-10-07

### Fixed

- **CBOM and SARIF output named the wrong tool.** Reports said they were
  generated by `slow_lynx` (CBOM) or `slow-lynx` (SARIF), names left over from
  the project 3329lens was extracted from. SARIF's `informationUri` also
  pointed at that project's private GitLab address, which returns 404 for
  everyone else. Both formats now name **3329lens**, link to
  <https://github.com/3329lens/3329lens>, and carry this crate's version.
- The SARIF fingerprint key in `partialFingerprints` is now `3329lens/v1`
  (was `slowLynx/v1`). If you already upload 3329lens SARIF to a code-scanning
  service, existing alerts may show up once as new and the old ones as fixed.
  After that they are tracked as before.

### Added

- `lens3329::tool::ToolInfo`, the name, version and information URI of the
  tool that produced a report. `ToolInfo::default()` is 3329lens itself.
- `cbom::findings_to_cbom_with_tool`, `cbom::Bom::with_tool` and
  `sarif::build_with_tool`, for programs that use this crate as a library and
  want their own name in the output. The existing `findings_to_cbom`,
  `Bom::new` and `sarif::build` keep their signatures and now use the
  default, so only their output changes.

## [0.2.0] - 2026-10-07

### Changed

- **Breaking (`cli` feature only):** upgraded `ratatui` 0.26 → 0.30 and
  `crossterm` 0.27 → 0.29. The public `scanner_dashboard` module exposes
  types from these crates in its signatures, for example
  `scanner_dashboard::ui::render(&mut ratatui::Frame, ..)`, so code that calls
  it must use the same `ratatui` version. The scanning and correlation modules
  (`scanner`, `lockfile`, `advisories`, `pep440`, `library`, `cbom`, `sarif`)
  are unchanged.
- **Minimum supported Rust version is now 1.88**, declared as `rust-version`
  in `Cargo.toml`. `ratatui` 0.30 requires it. Older toolchains now get a clear
  "requires rustc 1.88" error from Cargo. This applies to the whole crate,
  including `default-features = false` builds.
- The README install section now has per-platform steps for Linux, macOS,
  Windows and WSL, and recommends `cargo install --locked`.

### Security

- Removes `lru` 0.12, which `ratatui` 0.26 pulled in and which is affected by
  RUSTSEC-2026-0002 (`IterMut` violates Stacked Borrows) and RUSTSEC-2026-0253
  (`pop()` is not panic-safe). Neither was reachable from 3329lens: its only
  `lru` use was `ratatui`'s private layout cache, which calls only `new()`
  and `get_or_insert()`. `ratatui` 0.30 uses `lru` 0.18. `cargo audit` now
  reports no vulnerabilities and no warnings.

## [0.1.0] - 2026-09-25

First release. Scans a codebase for the cryptography it depends on,
resolves versions from Cargo, npm and PyPI lockfiles, correlates them against
an offline RustSec/OSV advisory database, and exports text, JSON, CycloneDX 1.6
CBOM or SARIF 2.1.0. Includes an interactive terminal dashboard.
